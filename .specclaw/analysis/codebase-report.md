## Tech Stack

- Backend is classic .NET Framework, not .NET Core: `DM.Core/DM.Core.csproj` (and all other `.csproj` files opened) declare `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>` inside an MSBuild `ToolsVersion="14.0"`/`"15.0"` project format, using `packages.config`-style NuGet restore (`<Import Project="..\packages\EntityFramework.6.4.4\build\EntityFramework.props" ...>`).
- Server project `DM.Server/DM.Server.csproj` is an ASP.NET Web API 2 + OWIN host: it lists `<Reference Include="System.Web.Http, ...">`, `<Reference Include="Microsoft.Owin.Host.SystemWeb">`, and Startup wiring in `DM.Server/Global.asax.cs` (`GlobalConfiguration.Configure(WebApiConfig.Register)`), matching the README's claim ("Asp.Net Web API 2"). Its `RootNamespace` is actually `DM.AuthServer` per the csproj, and `DM.Server/Controllers/PatientController.cs` and `DM.Server/Controllers/BaseController.cs` are both declared `namespace DM.AuthServer.Controllers` — the physical project name (`DM.Server`) and its .NET namespace (`DM.AuthServer`) diverge.
- Data access uses Entity Framework 6 (Database-First/Code-First hybrid with migrations): `DM.Models/DM.Models.csproj` references `EntityFramework, Version=6.0.0.0` via `..\packages\EntityFramework.6.4.4\...` and includes dozens of `Migrations\*.cs`/`*.Designer.cs` pairs going back to `201512281828016_InitialCreate.cs` through `202509030639057_Patient_Code_Unique.cs`.
- DI container is Unity: `DM.Server/App_Start/UnityConfig.cs` calls `container.RegisterTypes(AllClasses.FromAssemblies(BuildManager.GetReferencedAssemblies().Cast<Assembly>()), WithMappings.FromMatchingInterface, ...)` — convention-based auto-registration of every Contacts-interface-to-implementation pair across assemblies, and `Unity.WebApi`'s `UnityDependencyResolver` is wired into `GlobalConfiguration.Configuration.DependencyResolver`.
- Auth is ASP.NET Identity + OWIN OAuth bearer tokens: `DM.Server/App_Start/UnityConfig.cs` registers `ApplicationDbContext` (Identity's own EF context, defined in `DM.Server/Models/ApplicationDbContext.cs` per the csproj compile list) alongside a second, separate `DentalDbContext`. `DM.Server/Web.config` sets `<authentication mode="None" />` (auth is handled by the OWIN pipeline/`[Authorize]` attribute, not classic ASP.NET forms auth), confirmed by `[Authorize]` on `DM.Server/Controllers/PatientController.cs` and `DM.Server/Controllers/BaseController.cs`.
- Frontend is AngularJS 1.x, not a modern SPA framework and not npm/webpack-built: `Client/app/scripts/` contains hand-written `*.config.js` / `*.controller.js` / `*.service.js` files per feature (e.g. `Client/app/scripts/patient/patient.controller.js`, `Client/app/scripts/dashboard/dashboard.config.js`), and third-party Angular libraries are vendored directly under `Client/Scripts/angular-strap/` and `Client/Scripts/angular-ui/` rather than fetched by a package manager for the app itself.
- `Client/package.json` (`"name": "tilespad-dist"`) is a Gulp build-tooling manifest, not the AngularJS app's dependency manifest — its `dependencies` list is entirely Gulp plugins (`gulp`, `gulp-uglify`, `gulp-imagemin`, `gulp-jshint`, etc.), confirming the client is bundled/minified with a Gulpfile (`Client/Gulpfile.js`) rather than a modern JS package ecosystem.

## Structure/Architecture

- The solution is a classic layered/N-tier .NET architecture, and the directory names accurately describe their contents: `DM.Repository/DM.Repository.csproj` compiles `AppointmentRepository.cs`, `DoctorRepository.cs`, `PatientCreateRepository.cs`, `PaymentRepository.cs`, etc. plus matching interfaces under `Contacts\I*Repository.cs`; `DM.Service/DM.Service.csproj` compiles the corresponding `*Service.cs` classes and `Contacts\I*Service.cs` interfaces. I opened `DM.Repository/BaseRepository.cs` and `DM.Repository/PatientCreateRepository.cs` directly and confirmed they contain exactly what the naming implies (generic EF CRUD base class; a patient-specific repository with `GetPatientByCode`).
- The `dependency_graph` from collected facts and my reading of the `.csproj` files agree on the layering direction: `DM.Repository` → `DM.Models` + `DM.RequestModels` + `DM.ViewModels`; `DM.Service` → `DM.Models` + `DM.Repository` + `DM.RequestModels` + `DM.ResponseModels` + `DM.ViewModels`; `DM.Server` → all of the above plus `DM.Core`. This is a textbook Controller → Service → Repository → Models flow, confirmed end-to-end by reading `DM.Server/Controllers/PatientController.cs` (injects `IPatientCreateService`/`IPrescriptionService`), `DM.Repository/PatientCreateRepository.cs` (injects `DentalDbContext`), and `DM.Models/DentalDbContext.cs` (defines the `DbSet<>`s).
- `DM.Server` is not purely the domain API server — its `.csproj` `RootNamespace` is `DM.AuthServer` and it directly contains its own `Repository/` and `Service/` folders (`Repository\PermissionRepository.cs`, `Repository\RoleRepository.cs`, `Repository\UserRepository.cs`, `Service\PermissionService.cs`, `Service\RoleService.cs`, `Service\UserService.cs`) and an `ApplicationDbContext` under `Models\ApplicationDbContext.cs` — i.e. identity/authz/permission concerns are implemented directly inside the web project rather than through the `DM.Repository`/`DM.Service` layering used for the rest of the domain. This is a real architectural split I can confirm from the `.csproj`'s own `<Compile Include>` list, though I did not open every one of those files individually.
- Two separate `DbContext` types are registered side-by-side for what looks like a single logical database: `DM.Server/App_Start/UnityConfig.cs` registers both `container.RegisterType<DbContext, ApplicationDbContext>(...)` and `container.RegisterType<DbContext, DentalDbContext>(...)`. `DM.Models/DentalDbContext.cs` contains a static constructor with the comment `// The schema is owned by ApplicationDbContext's migrations, so skip EF's model-hash check for this context.` followed by `Database.SetInitializer<DentalDbContext>(null);` — this is direct, first-party confirmation that the two EF contexts intentionally share one physical database/schema but maintain separate, independently-versioned EF Migrations histories (`DM.Models/Migrations/*` vs `DM.Server/Migrations/*`).
- The Angular client mirrors the server-side domain module-by-module: `Client/app/scripts/` has one folder per feature area (`patient/`, `product/`, `stock/`, `auth/`, `dashboard/`, `user/`, `about/`), each with its own `*.config.js` (route registration), `*.controller.js`, and `*.service.js`, matching the `DM.Server/Controllers/*Controller.cs` feature set (`PatientController`, `ProductController`, `InventoryController`, `AppointmentController`, `DoctorController`, etc.) I saw listed in `DM.Server/DM.Server.csproj`.
- `DM.Server.Tests/` exists as a real MSTest project on disk (`DM.Server.Tests/DM.Server.Tests.csproj`, `DM.Server.Tests/UnitTest1.cs`) and is registered in `DentalManagement.sln`, but the collected-facts `test_locations` array came back empty — confirming this is a collector gap for this repo layout, not evidence of a missing test project.

## Domain

Inference: This is a single-clinic dental-practice management system covering patient records, prescriptions/treatments, payments, appointments/doctors, and inventory/stock of dental products — based on `README.md`'s title "Dental Management System (Prescription and Inventory)", the entity set in `DM.Models/DentalDbContext.cs` (`Patients`, `Prescriptions`, `PatientMedicalServices`, `PatientMedicalInfos`, `Payments`, `Doctors`, `Appointments`, `Products`, `Inventories`), and the matching Angular feature folders `Client/app/scripts/patient/`, `.../product/`, `.../stock/`.
Inference: The system enforces a business rule that each patient has a unique, human-assigned code of 7–8 characters rather than a purely system-generated ID — from `DM.Models/Patient.cs`'s `[StringLength(8, MinimumLength = 7)]` on `Code`, and `DM.Models/DentalDbContext.cs`'s `modelBuilder.Entity<Patient>().HasIndex(p => p.Code).IsUnique();`, reinforced by the recent migration `DM.Models/Migrations/202509030639057_Patient_Code_Unique.cs` visible in the `.csproj`.
Inference: A "current prescription" / running balance concept exists per patient visit — `DM.Server/Controllers/PatientController.cs` calls `_prescriptionService.GetPatientCurrentPrescription(patient.Id).Last()` and reads `prescription.TotalPayable`, `prescription.TotalPaid`, `prescription.TotalDue` onto the patient grid, suggesting prescriptions double as billing/visit records with due-balance tracking, not just medication records.
Inference (low confidence): The product is operated by (or was built for) a single named clinic rather than sold as multi-tenant software — the uncommitted `DM.Server/Web.config` diff still references a hardcoded database name `Initial Catalog=MahmudaDentalDb` and the top-level `README.md` mentions "MahmudaDental" only implicitly via this connection string; I did not find an explicit multi-tenant/customer-selection mechanism in the files I opened.

## Risks/Tech-Debt

- Real N+1 query / unhandled-exception risk in the patient list endpoint: `DM.Server/Controllers/PatientController.cs`'s `Get()` and `Search()` both load `_patientCreateService.GetAll()` (all patients) and then, inside a `foreach`, call `_prescriptionService.GetPatientCurrentPrescription(patient.Id).Last()` for every single patient — one extra query per patient, and `.Last()` on a possibly-empty sequence (e.g. a patient with no prescriptions yet) will throw `InvalidOperationException` and take down the whole grid/search request. I read this code directly; it is not a guess.
- Two independently-versioned EF Migrations histories against what the code's own comment says is one shared schema: `DM.Models/DentalDbContext.cs`'s static constructor explicitly disables EF's model-hash safety check (`Database.SetInitializer<DentalDbContext>(null);`) with the comment "The schema is owned by ApplicationDbContext's migrations, so skip EF's model-hash check for this context." This is a deliberate workaround for a genuinely fragile setup — any future schema change made through `DM.Models/Migrations/` without corresponding care in `DM.Server/Migrations/` (or vice versa) has no automatic EF safety net to catch a mismatch.
- Test coverage is effectively nil despite a real test project existing: `DM.Server.Tests/UnitTest1.cs` is the entire test suite, and its one test is `[TestMethod] public void TestMethod1() { }` — an empty auto-generated stub with no assertions. There are no other test files anywhere in the collected file enumeration. Given the layered service/repository architecture (interfaces exist for every repository/service, ideal for mocking), this represents a large gap between architectural intent and actual verification.
- Dependency versions are old and hand-pinned via `<HintPath>`, with at least one live inconsistency caught mid-fix: the working-tree diff in `DM.Server/DM.Server.csproj` changes `Microsoft.AspNet.Identity.Owin.2.2.1` to `...2.2.4` in the `<HintPath>`, while `Microsoft.AspNet.Identity.Core` and `Microsoft.AspNet.Identity.EntityFramework` in the same file remain pinned at `2.2.1` — i.e. this project has (or very recently had) mismatched Identity package versions across the Identity family, which is exactly the kind of drift that classic-`packages.config`/`HintPath` projects are prone to versus a modern PackageReference-based restore.
- The uncommitted `DM.Server/Web.config` diff changes the SQL Server connection string from `Data Source=.\SQLEXPRESS` to `Data Source=.` — a local dev-environment change (default instance vs. named `SQLEXPRESS` instance) currently sitting uncommitted in the working tree per `git status`, alongside the `.csproj` and `DentalDbContext.cs` changes; none of these three files' changes have been committed, so the repository's current on-disk state does not match its last commit.
- `DM.Server/DM.Server.csproj` references seven separate OWIN social-login providers (`Microsoft.Owin.Security.Facebook`, `.Google`, `.Twitter`, `.MicrosoftAccount`, plus `.Cookies`/`.OAuth`) inherited from the original ASP.NET Identity template; combined with MVC/Razor/Bundling references (`Microsoft.AspNet.Mvc.5.2.3`, `System.Web.Optimization`) that appear unused by the Web-API-only controller set I saw, this suggests template cruft that increases the attack surface and package-update burden without corresponding functionality — I did not confirm whether any social-login provider is actually configured/enabled at runtime (that would require reading `App_Start/Startup.Auth.cs`, which I did not open), so I'm flagging the reference footprint, not confirmed dead code.

## Suggested First Changes

- Start in `DM.Server/Controllers/PatientController.cs` if working on the patient list/search feature — it is short, self-contained, and directly demonstrates the project's Controller → Service → ViewModel pattern; fixing the `.Last()`/N+1 issue there (see Risks) would be a good low-risk, high-value first task and a way to exercise the full request path end-to-end.
- Trace `DM.Repository/BaseRepository.cs` → `DM.Repository/PatientCreateRepository.cs` → `DM.Models/DentalDbContext.cs` before touching any data-access code — this three-file chain is the minimum needed to understand how every other `*Repository.cs` in `DM.Repository/` is built (they all extend the same generic base and inject the same `DentalDbContext`).
- Read `DM.Server/App_Start/UnityConfig.cs` before adding any new service/repository/controller — because registration is convention-based (`WithMappings.FromMatchingInterface`), a new class will be auto-wired into DI purely by implementing an interface with a matching name in its `Contacts\` folder; no explicit registration line needs to be added, which is easy to miss coming from projects that use explicit DI registration.
- If asked to add or fix tests, start by replacing the stub in `DM.Server.Tests/UnitTest1.cs` rather than assuming test infrastructure needs to be built from scratch — the MSTest project, references, and solution wiring already exist; only actual test content is missing.
- Before touching schema/migrations, read both `DM.Models/Migrations/Configuration.cs` and `DM.Server/Migrations/Configuration.cs` (both exist per the `.csproj` compile lists) together with `DM.Models/DentalDbContext.cs`'s static constructor — given the two independently-migrated `DbContext`s share one physical database, a migration added to the wrong project's `Migrations/` folder could silently diverge from the actual schema with no EF-level warning.
