# DM.Baseline.Harness

Golden-master capture harness for the Dental Management System legacy app
(`DentalManagement.sln`). Generated by `bf-baseline-designer` (harness mode)
from `.specclaw/baseline/scenarios.md` and `.specclaw/baseline/seams.md`.
Never run automatically by specclaw itself — a human runs it to actually
produce fixtures.

## Stack detected

- **Backend:** .NET Framework 4.8, ASP.NET Web API 2 + OWIN, Entity Framework
  6.4.4, Unity DI (bypassed here — see below). Confirmed directly from
  `DM.Server/DM.Server.csproj` (`<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>`),
  `DM.Models/DM.Models.csproj`'s EntityFramework 6.4.4 package reference, and
  `codebase-report.md`'s own Tech Stack section — all three agree.
- **`DM.Server`'s own project/assembly-name split:** the project folder/csproj
  file is named `DM.Server`, but its `RootNamespace`/`AssemblyName` are both
  `DM.AuthServer` (confirmed directly in `DM.Server/DM.Server.csproj`). This
  harness's project reference to `DM.Server.csproj` therefore pulls in an
  assembly literally called `DM.AuthServer.dll` — not a typo, matches the
  legacy repo's own divergence, already flagged in `codebase-report.md`.
- **Test framework:** `Microsoft.VisualStudio.QualityTools.UnitTestFramework`
  (legacy MSTest v1) — the same one the pre-existing, empty
  `DM.Server.Tests/UnitTest1.cs` stub already references. **There was no
  existing arrange pattern to imitate**: that stub's only test method is
  `{ }` (a no-op), with no database setup, no fixture builder, nothing. This
  harness had to establish its own arrange convention from scratch (see
  `Infrastructure/`) — it is not a reproduction of a house style, because
  none existed.
- **Why not a more modern runner (xUnit/NUnit/MSTest v2):** the legacy
  solution's own toolchain is a classic `packages.config`-restored, non-SDK
  `.csproj` targeting .NET Framework 4.8. Introducing a different test
  framework than the one already vendored (`DM.Server.Tests`'s own
  reference) would add a second, inconsistent testing convention to a repo
  that already has one, however thin. Reusing the same framework keeps this
  harness buildable with the exact same MSBuild/NuGet toolchain the rest of
  the solution already uses.

## What this harness does NOT do

- It never runs the legacy application itself.
- It never writes a fixture file as part of code generation — fixtures are
  only ever written when a human actually executes the compiled test
  binary (`FixtureWriter.cs`'s `Write(...)` is only ever called from inside
  a `[TestMethod]`).
- It never mutates `.specclaw/analysis/*` or `.specclaw/baseline/scenarios.md`/`seams.md`.

## One-time setup

1. **A SQL Server LocalDB instance must be reachable.** `App.config`'s
   `DefaultConnection` connection string points at
   `(localdb)\MSSQLLocalDB`, database `DM_Baseline_Harness` — a dedicated
   database, never the legacy app's own `MahmudaDentalDb`. If your machine
   uses a different LocalDB instance name (or SQL Server Express instead),
   edit that one connection string; both `DentalDbContext` and
   `ApplicationDbContext` read the same "DefaultConnection" name (confirmed
   by reading both contexts directly this run), so one edit covers both.
2. **Restore NuGet packages** for the whole solution first (this harness
   references the exact same package versions already restored under
   `packages/` at the repo root — it does not vendor its own copies):
   ```
   nuget restore DentalManagement.sln
   ```
3. **Build the harness project** (also builds every legacy project it
   references — DM.Models, DM.RequestModels, DM.Repository, DM.Service,
   DM.ViewModels, DM.Server/DM.AuthServer):
   ```
   msbuild .specclaw/baseline/harness/DM.Baseline.Harness/DM.Baseline.Harness.csproj /p:Configuration=Debug /t:Restore,Build
   ```

## Running the harness (produces fixtures)

```
vstest.console.exe .specclaw/baseline/harness/DM.Baseline.Harness/bin/Debug/DM.Baseline.Harness.dll
```

or, from Visual Studio: Test Explorer → Run All, after building the
`DM.Baseline.Harness` project.

The **first test run** in a fresh LocalDB database triggers
`Infrastructure/AssemblyInit.cs`'s `[AssemblyInitialize]`, which runs both
legacy EF6 migrations configurations (`DM.Models.Migrations.Configuration`
for `DentalDbContext`, `DM.AuthServer.Migrations.Configuration` for
`ApplicationDbContext`) via `DbMigrator.Update()` — the same mechanism
Visual Studio's own Package-Manager-Console `Update-Database` uses. This
also creates the LocalDB database itself if it does not exist yet, and runs
each Configuration's own `Seed(...)` (Statuses, the one seeded Doctor,
Roles, Resources, Permissions, the two seed Users). Subsequent runs skip
this (idempotent — see `TestDatabase.cs`).

Each of the 41 `[TestMethod]`s writes its own fixture to
`.specclaw/baseline/fixtures/<GM-ID>.json` on completion. After a full run,
41 files should exist there, one per scenario ID.

## Re-running / resetting

This harness's LocalDB database is **not** dropped or reset between runs —
re-running the test suite re-arranges and re-writes each scenario's own
fixture from a clean per-scenario state (`DbCleaner.cs`), but does not
reset the whole database. To force a truly clean slate (e.g. after editing
a migration), drop the `DM_Baseline_Harness` database yourself
(`sqllocaldb` / SSMS / `DROP DATABASE DM_Baseline_Harness;`) before the next
run — `EnsureSchemaAndSeed()` will recreate and re-seed it.

## Known assumptions worth double-checking on first run

- **`Infrastructure/OwinTestContext.cs`** fakes just enough of ASP.NET's
  ambient `HttpContext.Current`/OWIN state for `UserService`,
  `ProfileService`, `PermissionService`, `UserRepository`, and
  `ProfileRepository`'s own constructors/methods (all of which read
  `HttpContext.Current.GetOwinContext().GetUserManager<ApplicationUserManager>()`
  and/or `HttpContext.Current.User.Identity.GetUserId()` directly, confirmed
  by reading each file this run). It relies on `Microsoft.Owin.Host.SystemWeb`
  reading the OWIN environment dictionary from `HttpContext.Items["owin.Environment"]`
  — a convention documented in several published OWIN-unit-testing
  write-ups, but not independently re-confirmed against that package's own
  source this run (it is a NuGet binary, not part of this repo). If any of
  the MOD-005 tests (GM-026 through GM-040) fail to construct their
  controller/service at all (as opposed to a legitimate captured-behaviour
  assertion failure), this is the first place to check.
- **`Infrastructure\ReflectionHelpers.cs`** constructs both legacy
  `Migrations.Configuration` classes via `Activator.CreateInstance(type, nonPublic: true)`
  and invokes `AddPermissions` via `MethodInfo.Invoke` with
  `BindingFlags.NonPublic` — both are because the legacy classes are
  `internal`/`private static`, matching how EF6's own tooling already calls
  them; not a modification of the legacy source.

## Files

- `DM.Baseline.Harness/DM.Baseline.Harness.csproj` — the harness project
  (classic, non-SDK `.csproj`, `packages.config`-restored, matching the
  legacy solution's own convention).
- `DM.Baseline.Harness/Infrastructure/` — shared arrange/fixture-writer
  helpers (`FixtureWriter.cs`, `TestDatabase.cs`, `DbCleaner.cs`,
  `OwinTestContext.cs`, `ReflectionHelpers.cs`, `DomainSeed.cs`, `GitInfo.cs`,
  `RepoPaths.cs`, `AssemblyInit.cs`).
- `DM.Baseline.Harness/Scenarios/` — one `[TestClass]` per related group of
  scenario IDs, one `[TestMethod]` per `GM-NNN` (41 total, matching
  `scenarios.md` one-for-one).
- `../error-map.md` — this project's own semantic error-code vocabulary
  (`DUPLICATE_NAME`, `CANNOT_DELETE_OWN_ACCOUNT`, `PASSWORD_RETYPE_MISMATCH`,
  `INVALID_CURRENT_PASSWORD`, `EMPTY_MEDICAL_INFO_LIST`, `NON_INTEGER_CHARGE`).
- `harness-manifest.json` — build/run commands and stack metadata, per
  `templates/CONTRACT.md` (d).
