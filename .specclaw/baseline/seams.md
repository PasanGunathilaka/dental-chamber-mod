## Seam Ranking

### Pure-function seams (`seam_layer: pure-function`) — lowest cost, highest fidelity

These have no DB and no clock dependency; they should be captured first.

- **`DM.RequestModels/HelperRequestModel.GenerateBillCode(string patientCode, string right)`** (`HelperRequestModel.cs:12-24`) — zero-pads to 3 digits, prefixes `"BILL"`, appends `"-" + patientCode`. Backs DR-003.
- **`DM.RequestModels/HelperRequestModel.GenerateAppointmentCode(string right)`** (`HelperRequestModel.cs:42-53`) — same 3-digit-pad shape, prefix `"AP"`. Used by `DM.Server/Controllers/AppointmentController.cs:55`. Not pinned by any numbered DR rule and not one of the three extra-scenario categories (cascade/boundary-computed-property/dual-mechanism), so it is listed here as seam evidence only — no scenario is derived from it in this design.

### Data/persistence-boundary seams (`seam_layer: persistence`)

- **EF6's default cascade-delete convention on every `[Required] Guid` foreign key**, confirmed by reading every entity's FK declaration directly and confirming `DM.Models/DentalDbContext.cs:44-52`'s `OnModelCreating` adds no Fluent API override disabling it:
  - `Patient` (1) → `Prescription` (required `PatientId`, `Prescription.cs:20-21`) → `PatientMedicalService` (required `PrescriptionId`, `PatientMedicalService.cs:16-17`) and → `Payment` (required `PrescriptionId`, `Payment.cs:13-14`) — a real, reachable multi-level cascade via `DM.Server/Controllers/PatientCreateController.cs:91-96`'s `Delete`.
  - `Product` (1) → `Inventory` (required `ProductId`, `Inventory.cs:17-18`) — reachable via `DM.Server/Controllers/ProductController.cs:119-124`'s `Delete`.
  - `Doctor` (1) → `Appointment` (required `DoctorId`, `Appointment.cs:37-38`) — cascade is configured at the DB level but **not reachable**: `DM.Server/Controllers/DoctorController.cs` exposes only `GetAll`/`GetById` (confirmed directly, no `Delete` action exists). See "No Legacy Behaviour Exists."
  - `Status` (1) → `Prescription`/`Product`/`Inventory`/`Appointment` (all required `StatusId int`) — cascade is likewise configured at the DB level (no diamond/multi-path conflict, since each of the four children has exactly one independent FK to `Status`) but **not reachable**: no controller/service/repository anywhere creates, updates, or deletes a `Status` row outside the one-time migration seed (confirmed by my own `Read` of every file `module-map.md`'s own "Unassigned" section names, plus my own search for any `Status`-mutating code path). See "No Legacy Behaviour Exists."
  - `Prescription` → `PatientMedicalService`/`Payment` is also configured, but its **own dedicated trigger** (`PrescriptionController.Delete`) is a no-op stub — see PQ-007 and "No Legacy Behaviour Exists." The same cascade is still reachable indirectly via the Patient-level delete above.
- **The deliberate absence of any FK/navigation on `PatientMedicalInfo`** (`DM.Models/PatientMedicalInfo.cs` — plain `Guid PatientId`/`MedicalInfoId`, no `[ForeignKey]`, confirmed directly) — deleting a `Patient` does **not** cascade or null out that patient's `PatientMedicalInfo` rows; they become orphaned. This is the direct contrast case to the Patient→Prescription cascade above.
- **The DB unique-index violation underneath DR-017** (`MedicalService.cs:20`, `MedicalInfo.cs:12`, both `[Index("IX_Name", IsUnique = true)]`) — observed as a raw `DbUpdateException`/inner `SqlException` only when called directly against the repository/`DbContext`, bypassing `BaseService<T>.Add`'s blanket `catch (Exception)` (`DM.Service/BaseService.cs:40-55`), which otherwise swallows the specific exception and returns `false` for any failure cause. See Capture Blockers for why this is a genuine seam-layer trade-off, not just a preference.

### HTTP/API-boundary seams (`seam_layer: http`)

No scenario in this design targets `http` as its primary layer. Every one of the 20 numbered rules, and every additional cascade/boundary/dual-mechanism finding, is reachable at `pure-function`, `service`, or `persistence` — a strictly cheaper and more deterministic layer than routing a real OWIN/Web-API request through `[Authorize]`, model binding, and JSON (de)serialization. The one piece of real, evidenced behaviour that genuinely lives *only* at the HTTP boundary is the `[Authorize]`/`[Authorize(Roles = "SystemAdmin, Admin")]` attribute enforcement itself (e.g. `DM.Server/Controllers/UserController.cs:9`, `DM.Server/Controllers/PatientController.cs:13`) — but that attribute-driven gate is not one of `domain-model.md`'s 20 numbered business rules, so no scenario is derived from it in this design; it is named here only so a future design pass does not overlook it as a legitimate `http`-layer candidate.

## Excluded: UI Automation

The legacy client is an AngularJS 1.x SPA (`Client/app/scripts/**`, confirmed via `codebase-report.md`'s Tech Stack section and my own directory read). The rebuild target, per `decisions.md`'s SQ-001/SQ-006, is React + TypeScript + Material UI — an entirely different component/rendering paradigm with no AngularJS `$scope`/`ng-model`/UI-Router concept to translate into. Any UI-driven test authored against the legacy DOM (e.g., a Protractor-style script exercising `patient-detail.tpl.html`'s tabs) would exercise AngularJS digest cycles, `$http` interceptors, and `ui-router` state transitions that have no equivalent surface in a React/MUI component tree — none of that automation could be replayed against the rebuild at all, let alone meaningfully. `decisions.md`'s SQ-013 additionally sets UI fidelity to THEME-ONLY (preserve palette/branding, not pixel-for-pixel layout), further reducing any residual value a legacy UI-level capture might have offered. UI parity in this project is established separately, by a human signing `ui-review.md` against hashed screenshots (`CONTRACT.md` (f)) — never by a golden-master seam.

## Capture Blockers (Determinism Audit)

1. **Unguarded `DateTime.Now`/`.ToLocalTime()` writes, both server- and client-side, with no injected clock.**
   - Server: `DM.Server/Controllers/PatientCreateController.cs:70-71` (`Prescription.Created`/`LastUpdate = DateTime.Now.ToLocalTime()`), `DM.Models/Migrations/Configuration.cs:39-40` (`Doctor.Created`/`LastUpdate = DateTime.Now`), `DM.Server/Migrations/Configuration.cs` seed users (`SecurityStamp`/timestamps via `Guid.NewGuid()`, not clock-based, but the surrounding seed rows carry no explicit timestamp field at all for `ApplicationUser` beyond what Identity itself manages).
   - Client (feeds server writes verbatim, no server-side recomputation): `Client/app/scripts/patient/patient-detail.controller.js:145-146,169,175,233,239`, `Client/app/scripts/stock/stock.controller.js:8` — all `new Date().toLocaleString()`.
   - None of the 20 numbered business rules computes a *verdict* by comparing a stored date to "today" (the closest candidate, `InventoryRepository.GetProductHistory`'s `DateTime.Now.AddMonths(-1)`/`AddDays(-model.DaysFilterId)` day-filter at `InventoryRepository.cs:24`, backs capability #18 "View stock-movement history," not one of DR-001..020, so no scenario targets it in this design — flagged here only so it is not silently missed by a future pass).
   - **Mitigation recommended: Option 2 (normalize the field out of comparison) for every scenario whose `Created`/`LastUpdate` field is not itself the rule under test** (i.e., every scenario in this design) — cheap, and loses no coverage of a rule that doesn't key off the value. `normalized_fields` entries: e.g. `output.prescription.created`, `output.prescription.last_update` (canonical paths per `CONTRACT.md` (g), resolved against each fixture's own real shape at record time). **This should also become a `TARGET-GAP`-shaped question for `/specclaw:bf-clarify`** — every one of these unguarded writes implies the rebuild needs an injectable clock (Option 1's ADR) if any *future* rule ever keys off them; none of `pending-questions.md`'s existing entries or `decisions.md`'s existing CQs/SQs cover this specifically, so it is a genuine open item for a future clarify pass, not raised as its own PQ here since it blocks no scenario in this design.

2. **Sequence-derived "auto-increment-like" values computed from a live row count at request time** — not a database `IDENTITY` column, but the same class of non-determinism: `HelperRequestModel.GetThisPatientCode`/`GenerateBillCode`/`GenerateAppointmentCode` are all fed a `Count() + 1` computed from the current row count (`PatientCreateController.cs:52`, `PrescriptionController.cs:51`, `AppointmentController.cs:53`). A fixture's `input` must record (and its `Arrange` step must precisely control) the exact pre-existing row count at Act time, or the generated code is unreproducible on replay.
   - **Mitigation recommended: Option 3-equivalent — pin the arrange-time row count exactly and assert the generated code directly** (the code's *format*, not its absolute uniqueness across all time, is what DR-001/DR-003 actually specify) rather than normalizing the field out, since the format itself is the rule under test in GM-001/GM-004.

3. **Genuine database-generated identity/GUID values, if ever compared raw.** `MedicalService.Code` (`[DatabaseGenerated(DatabaseGeneratedOption.Identity)] int`, `MedicalService.cs:14-16`) and every entity's `Guid Id` primary key. Comparing either across two independently-seeded databases is guaranteed noise. **Mitigation: `normalized_fields` (canonical path, e.g. `medical_service.code`, `patient.id`) wherever such a value is genuinely part of the output shape — never asserted directly, per `CONTRACT.md` (g)/(k).** No scenario in this design pins identity/idempotency as its actual rule (DR-002's "auto-provision on create" is a one-shot action, not a "call twice" idempotency check), so the `first_call_created`/`second_call_same_entity` boolean-assertion pattern is not required by any scenario here.

4. **Unstable ordering on ties.** `AppointmentRepository.GetByDate`'s `.OrderBy(x => x.Time)` (`AppointmentRepository.cs:28`) and `PrescriptionService.GetPatientCurrentPrescription`'s `.OrderBy(x => x.Code)` (`PrescriptionService.cs:24`) are both deterministic *given distinct sort-key values*, but neither query carries a tiebreaker column. LINQ-to-Entities translates `OrderBy` to a SQL Server `ORDER BY` with no guaranteed-stable tie order when two rows share the exact same `Time`/`Code`. **Mitigation: Option 3 — the Arrange step for GM-025 (DR-010) and GM-011 (dual-mechanism finding) must seed rows with distinct `Time`/`Code` values, avoiding the tie condition entirely, rather than relying on incidental DB tie-break stability.** This should also become a `TARGET-GAP`-shaped question for `/specclaw:bf-clarify` if the rebuild's own ordering ever needs a documented tiebreaker column — not raised as its own PQ here since no scenario in this design actually needs to observe a tie.

5. **`BaseService<T>.Add`/`Edit`/`Delete`'s blanket `catch (Exception)` (`DM.Service/BaseService.cs:40-105`) discards the specific failure cause.** This is not itself a clock/identity/ordering issue, but it is a genuine capture-fidelity blocker worth stating plainly here: at the `service` layer, *any* failure — a unique-constraint violation, a connection timeout, a concurrency conflict — surfaces identically as `false`, `threw: false`. A scenario captured only at this layer cannot distinguish "duplicate name" from "any other database error." This is why GM-013 (DR-017, `service`) and GM-014 (DR-017, `persistence`) are both designed — the `persistence`-layer variant is the only one that can record the raw `ExceptionType`/`ExceptionMessage` evidence per `CONTRACT.md` (b.2).

## Recommended Seam

**No single layer suffices for this application — the recommendation is layer-per-rule-class, not one seam:**

1. **Start with `pure-function`** (GM-001, GM-004, GM-016, GM-017, GM-041) — zero arrange cost, no DB, no clock, highest fidelity. Capture these first, as `templates/seams.md`'s own ordering guidance directs.
2. **`service` is the dominant layer for this codebase** — the overwhelming majority of the 20 numbered rules (DR-002, DR-004 through DR-018 except DR-017's persistence variant, DR-020) are most cheaply and faithfully observed there, needing only an EF6/SQL-Server test-database arrange step per scenario, no HTTP transport, no OWIN pipeline, no UI.
3. **Reserve `persistence`** for the handful of scenarios where only the ORM/schema boundary reveals the true configured behaviour: the two reachable cascade deletes (GM-012, GM-024), the one confirmed no-cascade orphan case (GM-019), and DR-017's raw-exception variant (GM-014).
4. **`http` is deliberately not used as a primary layer anywhere in this design** — every rule is reachable one layer lower, and CONTRACT.md (i) directs preferring the inner layer whenever the same rule is reachable there.

**A human should confirm this multi-layer recommendation (pure-function first, service as the dominant layer, persistence for cascade/constraint-specific cases, no http) before `--harness` generation proceeds.**
